# ChannelGuard-subscription

适用于 [ChannelGuard](https://github.com/azheng95/ChannelGuard) 的通知频道订阅：稳定的通用规则，加上供后续维护的扩展分组。

> 规则关闭的是整个通知频道，不是单条广告。排除词只能检查频道名称和 ID，不能识别通知正文。重要业务与营销共用一个频道时仍可能误拦截。移除订阅或关闭自动匹配不会自动恢复此前已被系统关闭的频道。

## 添加订阅

目标仓库为 `azheng95/ChannelGuard-subscription`。下面的地址须在将本项目上传到公开仓库的 `main` 分支后才能使用；本地创建项目不代表链接已经发布。

GitHub Raw：

```text
https://raw.githubusercontent.com/azheng95/ChannelGuard-subscription/main/subscription.json
```

CDN：

```text
https://cdn.jsdelivr.net/gh/azheng95/ChannelGuard-subscription@main/subscription.json
```

在 ChannelGuard 的“订阅”页添加其中一个地址，再在“设置”中开启自动匹配。已有通知频道可使用“立即扫描并应用”处理。

两个地址分发同一份订阅，`id` 均为 `channelguard-default`，只需添加一个。文件中的 `updateUrl` 刻意留空，客户端通过 URL 导入时会保存实际导入地址，后续沿用该地址更新。

尚未发布时，可先导入本地 [subscription.json](subscription.json) 验证。由于文件中的 `updateUrl` 为空，本地文件导入的订阅没有远程更新地址；发布后通过 URL 重新添加即可按同一订阅 ID 替换。

## 规则分组

| 分组 | 固定标识 | 默认状态 | 内容 |
|---|---|---|---|
| 通用规则 | `general` | 启用 | 营销、推广、促销、广告四条稳定规则 |
| 扩展规则 | `extended` | 关闭 | 初始为空，后续依据实际频道添加规则 |

通用规则覆盖所有应用，仅按频道名称中的“营销”“推广”“促销”“广告”四个关键词分别匹配，不使用频道 ID 作为正向条件，也不使用全频道匹配。

四条规则使用相同的中英文排除词，覆盖订单、支付、交易、退款、物流、验证码、登录、安全、通话、下载、上传、同步、前台服务、常驻、广告拦截及广告过滤服务。排除词同时检查频道名称和 ID，并优先于该条规则的正向匹配。

“活动”“推荐”“消息”等范围较广的词不属于通用规则。新增规则优先放入默认关闭的扩展分组，不随意扩大通用规则的匹配范围。后续添加扩展规则后，需在 ChannelGuard 中手动启用该分组才会参与匹配。

## 匹配行为

- 订阅、分组、规则均启用时才参与匹配；客户端还需开启自动匹配。
- 包名区分大小写，支持精确包名、`com.example.*` 前缀和 `*`。
- 频道关键词是不区分大小写的子串，不支持正则、精确匹配或“同时满足”条件。
- `channelNames` 与 `channelIds` 是“或”关系。
- `excludeKeywords` 仅排除所在规则，不是跨规则的全局放行名单。
- 按文件中的分组和规则顺序返回第一个命中项；跨订阅还受客户端订阅列表顺序影响。
- 单频道手动设置优先于订阅结果。手动放行可防止 ChannelGuard 再次自动拦截，但不保证恢复已被 Android 关闭的频道。

例如，“营销通知”会命中；“订单与营销”或 ID 包含 `PAYMENT` 的“营销通知”会被排除；只有 ID 含“营销”、名称为“普通通知”的频道不会命中通用规则。

## 检查规则

使用 Node.js 24 或更高版本，在本项目目录运行：

```powershell
npm run check
npm test
```

没有第三方依赖，无需运行 `npm install`。

校验器检查严格 JSON、必需字段、字段类型、合法日期、正的 32 位整数版本、唯一标识及匹配条件，拒绝未知字段和全应用全频道匹配。校验规则比客户端的宽松解析更严格，以免拼写错误或字段缺失被静默忽略。

测试固定通用规则的范围和排除词基线，覆盖正向命中、重要业务排除、大小写、开关、包名边界、规则顺序和空扩展分组。JavaScript 匹配器仅供回归测试，Android 客户端实现仍是行为依据；通过测试不代表系统 Hook 或实际频道关闭已经过设备验证。

## 发布与维护

1. 根据 [贡献说明](CONTRIBUTING.md) 修改规则并添加回归用例。
2. 保留订阅、分组及已有规则的标识；规则变更时递增 `subscription.json` 的 `version`，更新 `updatedAt` 为实际修改日期。
3. 运行检查和测试，再将变更提交至目标公开仓库的 `main` 分支。
4. 检查上方 Raw 地址返回 JSON，并测试 CDN 地址；CDN 缓存可能导致更新延迟。
5. 在 ChannelGuard 内点击订阅更新。客户端目前不会因版本号变化自行定时拉取，版本号也不是阻止旧文件覆盖的校验机制。

GitHub Actions 会在推送、Pull Request 或手动触发时运行相同检查，不修改规则、不递增版本、不自动提交。维护者应在合并或发布前确认检查通过。

遇到更新失败时先检查地址是否公开可访问、是否为 JSON 文件而非仓库网页。CDN 暂未更新或不可用时，可用 Raw 地址重新添加同一订阅；客户端会按 ID 替换并保留订阅启用状态，随后沿用新地址更新。

## 反馈误拦截

记录应用包名、应用版本、实际频道名称、频道 ID、订阅版本及预期行为，在目标仓库发布后通过 Issues 反馈。请勿提供通知正文中的验证码、账号等个人信息。

可先在 ChannelGuard 中对该频道手动放行；若 Android 仍保持频道关闭，还需到系统通知设置尝试恢复。不要直接把所有频道改为宽泛匹配来绕过问题。
